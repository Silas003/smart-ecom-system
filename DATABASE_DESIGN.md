# Relational Database Design (Smart E-Commerce System)

This document describes the relational database design, normalization decisions, primary/foreign keys, and constraints for the Smart E-Commerce System. The production schema is provided in `src/main/resources/sql/schema_postgres.sql`.

Overview of entities
- users: application users (customers, admins)
- categories: product categories
- products: product catalog
- inventory: source-of-truth stock (one-to-one with products)
- orders: customer orders
- order_items: items belonging to an order
- reviews: (optional relational store) reviews metadata; primary NoSQL store is recommended

Normalization and keys
- The schema is normalized to 3NF:
  - Repeating groups moved to separate tables (order_items)
  - Non-key attributes depend only on the key (no transitive dependencies)
  - Inventory kept as a separate table to allow inventory metadata (reserved quantity, status)

Primary & Foreign Keys
- `users.id` PK
- `categories.category_id` PK
- `products.product_id` PK, `products.category_id` FK -> `categories(category_id)`
- `inventory.id` PK; `inventory.product_id` UNIQUE FK -> `products(product_id)`
- `orders.order_id` PK; `orders.user_id` FK -> `users(id)`
- `order_items.id` PK; `order_items.order_id` FK -> `orders(order_id)`; `order_items.product_id` FK -> `products(product_id)`

Indexes
- See `src/main/resources/sql/create_indexes.sql` (functional index on LOWER(name), category_id, price, orders.user_id, etc.)
- Add indexes on foreign key columns for join performance.

Constraints & triggers
- NOT NULL constraints are applied where business logic requires (e.g., inventory.quantity_in_stock default 0)
- CHECK constraints can be added to enforce non-negative quantities and positive prices.

Data types
- Use PostgreSQL types:
  - SERIAL / BIGSERIAL not used; prefer `GENERATED BY DEFAULT AS IDENTITY` for SQL standard identity columns if desired.
  - Use TIMESTAMP WITH TIME ZONE (`timestamptz`) if timezone-aware timestamps are required.

ERD guidance
- Create an ERD showing:
  - users 1<--* orders
  - orders 1<--* order_items *-->1 products
  - products 1<--1 inventory
  - products *-->1 categories

Migration and deployment
- A set of Flyway migrations is included in `src/main/resources/db/migration` (V1..V3). Use Flyway (Maven plugin configured) to apply migrations in a repeatable, versioned way.

Normalization proof (brief)
- Users and categories are separate entities (eliminates repeating groups).
- Products reference categories by foreign key; inventory stored separately to avoid nullable stock fields or repeated stock metadata.
- Orders and order_items separate transactional order header from line items (no multi-valued attributes in one table).

Recommended next steps
- Consider adding a `migrations/` changelog for larger changes and include data migrations where needed.
- Add a simple migration that seeds admin user with hashed password (avoid plain-text in production).

Refer to `docs/erd.svg` for a visual ERD and `src/main/resources/db/migration` for the migration scripts.

Sample questions
- Why separate inventory? Allows maintaining stock history and reservation fields without changing the product's core record.
- Reviews are best stored in MongoDB (see `NOSQL_DESIGN.md`), but a relational reviews table may be added for strict ACID requirements.

Refer to `src/main/resources/sql/schema_postgres.sql` for the full SQL.
